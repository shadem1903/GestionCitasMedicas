Comunicación entre Servicios + REST + Eventos

Equipo: Arquitectura Sistema de Citas

Proyecto: Plataforma de Gestión de Citas Médicas

🪜 1. Interacciones entre Servicios

Interacción 1 – Validación de disponibilidad antes de agendar

Servicio de Gestión de Citas
Servicio de Disponibilidad Médica
ID del médico, especialidad, fecha y hora solicitada. El sistema consulta si el horario está libre y si el médico está activo.
No se puede confirmar la cita. El sistema debe bloquear temporalmente la operación, aplicar reintentos automáticos y mostrar un mensaje controlado al usuario indicando que no se pudo verificar la disponibilidad.

Interacción 2 – Validación de identidad y permisos

Servicio de Gestión de Citas
Servicio de Usuarios y Autenticación
Token JWT del usuario autenticado, ID del paciente y del médico. Se valida que el paciente exista y que el usuario tenga permisos para crear la cita.
La cita no debe registrarse. El sistema cancela la operación para evitar inconsistencias o problemas de seguridad.

Interacción 3 – Notificación posterior a la creación de la cita

Servicio de Gestión de Citas
Servicio de Notificaciones
Evento: "Cita creada", incluyendo fecha, hora, médico y datos de contacto del paciente.
La cita ya fue registrada exitosamente. El evento queda almacenado en la cola de mensajes para ser procesado cuando el servicio esté disponible.

🪜 2. REST o Eventos

Interacción REST Evento ¿Por qué?
Validación de disponibilidad ✔ Se requiere respuesta inmediata para confirmar si el horario está libre antes de registrar la cita.
Validación de usuario ✔ Es necesario validar identidad y permisos en tiempo real para continuar la operación.
Envío de notificación ✔ Es un proceso posterior que no debe bloquear la creación de la cita.

🪜 3. Síncrono o Asíncrono

Interacción Síncrono Asíncrono Justificación
Validación de disponibilidad ✔ El sistema debe esperar confirmación para evitar doble asignación de horarios.
Validación de usuario ✔ Sin validación no se puede continuar con la operación.
Notificación ✔ No es crítica para la transacción principal; puede procesarse después.

🪜 4. Eventos Importantes del Sistema

1️⃣ Cita creada

2️⃣ Cita cancelada

3️⃣ Cita completada y enviada a historial clínico

🪜 5. Análisis de Fallos

Servicio de Gestión de Citas (núcleo del sistema)
Los pacientes no podrían agendar ni cancelar citas. El sistema perdería su funcionalidad principal y se generaría congestión administrativa.
Debe continuar parcialmente. Otros servicios como historial o catálogo de especialidades pueden seguir funcionando.
Implementando Circuit Breaker, balanceo de carga, réplicas activas, reintentos automáticos con backoff exponencial y monitoreo en tiempo real.

🪜 6. Service Discovery

Los demás servicios no podrían localizarlo, provocando fallos de comunicación.
Consultando un registro central dinámico donde los servicios se registran automáticamente al iniciar.
Permite escalabilidad automática, tolerancia a fallos y despliegue dinámico sin configuraciones manuales.
Entre todos los microservicios para permitir que el servicio de citas encuentre automáticamente al de disponibilidad, usuarios y notificaciones.

🪜 7. Mini Diagrama

💡 Resumen Técnico
Las validaciones críticas usan comunicación REST síncrona.
Las notificaciones usan eventos asíncronos.
Service Discovery permite encontrar servicios dinámicamente.
El núcleo del sistema debe tener alta disponibilidad.
